# 03.4.2.2. Join a carrier while publishing its peers

Part of [03.4.2](../03.4.2-audit-loops-and-shared-ownership.md). The two-drain
regression in [03.4.2.1](03.4.2.1-carry-peer-backings-through-loops.md) publishes every worker before either drain starts. This
case interleaves publication and collection in **the same loop**. It uses safe
Rust threads, strong `Arc`, `Vec`, and ordinary drops from the operation matrix.

## Source cases

Start from `peer_backing_survives_until_its_own_drain` and its shared
`peer_program` fixture in the feature checkout. Keep the arithmetic lemma,
symbolic `u16` inputs, the zero-visit case and the final drain of the peers.

1. Keep only the peers vector. On each visit construct the buffer, clone its
   `Arc`, push the worker returning the clone, then spawn a locally held worker
   returning the original. Immediately join the local worker and drop its result.
   The loop invariant includes `peers.len() == i`. The original verifier reported
   `cannot release a shared backing while an indexed peer can still own it` at
   the drop. At `n == 2 && b == 19`, the post-loop checkpoint verifies
   **166 bytes** and rejects 165. This comprises 6 scalar bytes, 24 bytes for
   the vector, 16 bytes for its slots, two tags and two 59-byte backings.
2. Keep both vectors and push the carrying handle into its vector before popping
   and joining it in the same iteration. Use `handles.len() == 0` at each head.
   The original diagnostics included `cannot establish the selected worker's
   family and result description` at the pop and `cannot locate the selected
   worker's retained shared backing` at join. The empty vector still reserves
   its 16 slot bytes. The same checkpoint verifies **206 bytes** and rejects 205.

## Verification evidence

Feature revision `8e4dde1f8` adds
`immediate_join_preserves_backings_across_publications`. It runs three source
programs with symbolic worker count and buffer capacity. At two pairs of workers
and 19 payload bytes per pair, the local checks give these bounds in bytes.

| Storage for the immediately joined handle | Second iteration, before allocation | After publication | After all peers are joined and dropped |
| --- | ---: | ---: | ---: |
| Local variable | 106 | 166 | 46 |
| Vector reserved for two handles | 146 | 206 | 86 |
| Initially empty vector, grown by the first push | 162 | 222 | 102 |

Each of the first two numeric columns has a separate one-byte-short regression.
The zero-visit paths retain only the scalars and vector headers (30 or 54 bytes).
Dropping the vectors leaves six scalar bytes in all three programs. Every run
checks the independent global concurrent-contract diagnostic at the default
solver limit.

The loop proof counts surviving backings before the next allocation. A site
that never transfers its backing to a surviving peer proves its additional
charge is zero. The source regressions
`two_retained_results_release_their_own_visit` and
`repeated_coordinator_visits_release_the_current_visits_shared_buffer` check
that case. Full suite results are in the [parent audit](../03.4.2-audit-loops-and-shared-ownership.md#validation).
