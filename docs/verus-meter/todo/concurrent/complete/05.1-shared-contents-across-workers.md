# 05.1. Shared contents across workers

Start from the fixed-worker mutex analysis in `b8e289e04`. Each worker already
checks the bytes it takes into its account at first access and hands back at
unlock. The missing link is what the next holder can read. Use two workers sharing
an initially empty `Arc<Mutex<Vec<Box<T>>>>`. One pushes once and one pops once.

## Completion in `b6d2185c8`

A fixed worker now checks its outgoing contents at the actual unlock. The next
worker on that mutex checks its operations against the initial contents and the
possible preceding releases. The history retains the source and allocation origins
even when different releases produce the same byte count. An immutable scalar can
size an explicit reservation in one worker and still contribute to another
worker’s bound.

With one push and one pop, the consumer proves 106 bytes and fails at 105 under
either join order. With separate mutexes, the same checkpoint proves 74 and fails
at 73. With two preceding pushes, one box can remain in the mutex when the pop
takes the other. That checkpoint passes at 146 and fails at 145. The tests also cover a replacement
that overlaps the removed box and a reservation sized by a producer-only capture.

The implementation explores up to 128 states per mutex. If a publication or update
cannot be expressed in the receiving scope, or the full history exceeds this limit,
the worker retains the unrestricted incoming contents. Acquisitions in loops are
tracked in 05.4. The local checks leave the total concurrent contract pending in 07.
