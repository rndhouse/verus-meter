# 03.3.3.1. Allocations across loop iterations

**Completed under [03.3.3 — Prove final release](../03.3.3-shared-final-release.md).** A loop can clone one buffer for all workers or allocate a fresh buffer on every visit. This task covers workers and returned aliases from different visits that remain live together.

## Work

- [x] Give each execution of the allocation site a distinct identity. Reuse the checked loop and enclosing worker coordinates where applicable. Every clone of the same allocation must keep its identity, including when one iteration publishes several workers.
- [x] Carry that identity from capture through handle collections, joins and retained results. When a result drops, reconcile its strong references against the allocation from its own visit. Cover publication that transfers the last handle held by the publisher.
- [x] Derive the buffer contribution from the distinct live allocations. Preserve symbolic worker counts and buffer sizes, and account separately for handles, control blocks and collection storage.

## Done when

Exercise two source programs that retain their workers' results until collection. In one, each worker returns a clone of a single buffer allocated before the loop. In the other, each returns a fresh buffer allocated inside the loop. For `n > 0` workers and capacity `b` bytes per buffer, establish buffer contributions of `b` and `n * b`, respectively. Use symbolic function budgets and fixed checkpoint values where required by the current contract syntax. Include overhead in each asserted total. Cover zero workers according to the actual lifetime of the publisher's handle.

With two fresh, nonempty buffers alive, a budget allowing only one buffer must fail. Drop one result while keeping the other and check the remaining bytes. In the shared case, dropping one result must keep the single backing live. Require a budget diagnostic at the default solver limit for a one-byte reduction at a live checkpoint. Positive cases must pass the local obligations before the global proof in 07.

## Implementation and validation

Feature commits `386c1c5c9` and `d6c418b90` preserve each allocation's identity and byte charge through capture, handle-vector storage, join and final drop. The source regressions are in `source/rust_verify_test/tests/resource/memory/worker_shared_ownership.rs` and its `occurrences.rs` submodule.

| Executable case | Checked local bound including overhead |
| --- | --- |
| One buffer shared by `n` workers | `9*n + b + 160` peak budget. For zero workers and a 19-byte buffer, the publisher still holds 97 bytes before dropping its handle. |
| A fresh buffer per visit | `8*n + n*(41+b) + 192` peak budget. With two 19-byte buffers, the checkpoint is 166 bytes with both jobs outstanding, 140 with both results retained and 73 after one drops. |
| Two workers share a fresh buffer on each visit | Four outstanding jobs from two visits occupy 208 bytes at `b = 19`. Either result can drop first once both have joined. An equal-sized buffer from a different visit cannot take over the charge. |

Lowering the live checkpoints by one byte produces a budget error at the default solver limit. A separate source case allocates different capacities on successive visits and checks that the surviving result retains its original capacity. The varying-capacity case has a bounded iteration count in its loop invariants. Exploring a looser bound also exposed expensive proof-expression construction. These programs use executable allocation, clone, join and drop operations. The symbolic fresh-buffer case supplies arithmetic facts about multiplication.

Releasing a charged result while its only surviving alias is in an unjoined peer can still fail the local proof. The verifier requires evidence that the allocation will stay charged.
