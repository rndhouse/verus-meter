# 05.4. Repeated acquisitions and loop-selected mutexes

Apply the preceding tasks to the symbolic loop and worker patterns supported by
03.3. Successive visits to one lock statement can acquire the same mutex again
or select different mutexes. Only the former can see an earlier visit’s writes
through that mutex.

## Work

- [x] Identify the selected allocation and each new acquisition using the existing
  worker and loop occurrence bindings. Repeated handles to one mutex share its
  contents. Distinct allocations created at the same constructor retain their
  own contents, reservations and element origins.
- [x] Carry the checked update across iterations, including zero iterations, a
  skipped write and reacquisition after release. Preserve symbolic counts and
  allocation sizes. Use the selected occurrence when a worker receives or returns
  ownership through an indexed handle collection.
- [x] Keep obligations whose identity or reservation cannot be established explicit.
  A shared source location, equal byte sizes or an unknown index cannot justify
  treating two allocations as identical or as disjoint.

## Completion evidence

- [x] With a symbolic iteration count, test repeated updates through aliases of
  one mutex. Check that a later acquisition sees the permitted updates, including
  an unchanged initial state when the loop does no work.
- [x] In a loop over distinct mutexes of the same type, select one whose contents
  differ from its neighbour’s. Prove the selected payload’s local bound, reject a
  claim that uses the neighbour’s smaller value, and preserve any popped owner
  across unlock. Keep worker collection order independent of write order.

## Implementation and validation

In `92bd6e071`, every unlock must preserve a set of symbolic contents established
at publication. With a three-byte initial reservation, a reader proves 73 local
bytes if the writer skips every iteration and 107 if a 37-byte replacement can
reach it. Both one-byte-short claims fail. Repeated appends can fail the unlock
obligation when later contents fall outside the proposed set.

Indexed joins of by-value mutexes preserve each producer’s reservation. After
unlock and mutex drop, neighbouring popped buffers require 27 and 28 total
bytes. A separate worker can drain the same collection. Indexed shared handles
with unresolved protected backing remain unsupported. Repeated lock operations
in fixed workers are covered. Repeatedly spawning a worker with a mutable shared
backing also needs a per-publication ownership and reservation proof.

The seven regressions are in
`source/rust_verify_test/tests/resource/memory/synchronization/shared_payloads/repeated.rs`.

133 upstream tests passed. One VIR and one upstream test were ignored.
