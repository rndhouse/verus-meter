# 05.1. Shared contents across workers

Start from the fixed-worker mutex analysis in `b8e289e04`. Each worker already
checks the bytes it takes into its account at first access and hands back at
unlock. The missing link is what the next holder can read. Use two workers sharing
an initially empty `Arc<Mutex<Vec<Box<T>>>>`. One pushes once and one pops once.

## Work

- [ ] Express each critical section’s outgoing contents in terms of its incoming
  contents, checked inputs and executable operations. Preserve allocation origins,
  logical length, explicitly reserved slots and the source condition on each exit.
  Another worker must be able to use the relation in its own proof scope.
- [ ] The first holder receives the initial contents. Each later holder receives
  the contents at the immediately preceding unlock of that mutex in the chosen
  execution. Preserve every feasible order and carry the input through unchanged
  on paths that leave the contents alone.
  Distinguish a new acquisition from an alias of an existing guard. Apply the
  native success, poison and `WouldBlock` rules established in 04.
- [ ] Use this relation when checking the source operations inside the next critical
  section. Preserve their ordinary byte accounting, including the transient when
  a replacement value is live before the displaced value drops.

## Completion evidence

- [ ] With both workers outstanding, cover both successful orders. Push then pop
  yields the pushed box and an empty vector. Pop then push yields no box and one
  occupied slot. Reversing the order of the joins must preserve both possibilities.
- [ ] Prove a local upper bound that requires knowing at most one box could have
  been pushed. Reject a bound that only fits the empty case. Repeat with distinct
  mutexes of the same type and show that a push on one cannot supply the other's pop.
