# 05.4. Repeated acquisitions and loop-selected mutexes

Apply the preceding tasks to the symbolic loop and worker patterns supported by
03.3. Successive visits to one lock statement can acquire the same mutex again
or select different mutexes. Only the former can see an earlier visit’s writes
through that mutex.

## Work

- [ ] Identify the selected allocation and each new acquisition using the existing
  worker and loop occurrence bindings. Repeated handles to one mutex share its
  contents. Distinct allocations created at the same constructor retain their
  own contents, reservations and element origins.
- [ ] Carry the checked update across iterations, including zero iterations, a
  skipped write and reacquisition after release. Preserve symbolic counts and
  allocation sizes. Use the selected occurrence when a worker receives or returns
  ownership through an indexed handle collection.
- [ ] Keep obligations whose identity or reservation cannot be established explicit.
  A shared source location, equal byte sizes or an unknown index cannot justify
  treating two allocations as identical or as disjoint.

## Completion evidence

- [ ] With a symbolic iteration count, test repeated updates through aliases of
  one mutex. Check that a later acquisition sees the permitted updates, including
  an unchanged initial state when the loop does no work.
- [ ] In a loop over distinct mutexes of the same type, select one whose contents
  differ from its neighbour’s. Prove the selected payload’s local bound, reject a
  claim that uses the neighbour’s smaller value, and preserve any popped owner
  across unlock. Keep worker collection order independent of write order.
