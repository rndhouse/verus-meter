# 05.3. Helpers and conditional paths

Use the transitions from 05.1 and the escaped ownership from 05.2 in ordinary
function summaries. A worker that conditionally pushes a box and unlocks inside
a helper should expose the same possible payloads as the direct implementation.
A release-only helper already works at `b8e289e04`.

## Work

- [ ] At each call, substitute the actual scalars, allocation origins, mutex and
  guard acquisition. Preserve the identity of a borrowed or returned guard.
  A helper that consumes the guard and mutates the contents must export the
  contents at its actual release, including through a nested call.
- [ ] Cover multiple accesses during one acquisition, branches that leave the
  payload unchanged, and early returns. Carry each branch’s returned ownership,
  held guards and caller-live storage into the corresponding continuation.
- [ ] Preserve the summary’s entry requirements and proof dependencies. Keep the
  guard/witness binding usable by the verified protocols in 06. Facts about
  custom operations and permit capacity come from their contracts in 06.

## Completion evidence

- [ ] Compare direct and factored code on both branches. Check the same allocation
  remains charged after escape and the same payload is visible to the next holder.
  At equivalent source points, allow for any modeled inline storage introduced
  by the helper. An extra live allocation in the helper must affect its bound.
- [ ] Exercise two aliases of one mutex, two independent mutexes, and a guard
  returned on one path and released on another. Reject a claim that uses the
  wrong mutex or extends protection beyond release, even with spare call budget.

Start with `source/vir/src/resource/memory/synchronization/helpers.rs`,
`source/vir/src/resource/memory/calls.rs` and the shared payload regressions.
Use the same checked summary interface for calls in workers and in ordinary functions.
